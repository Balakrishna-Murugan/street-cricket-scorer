Overview

This repository implements a lightweight cricket live-scoring app with two primary parts: a React + TypeScript client and a Node (TypeScript) Express server with MongoDB (Mongoose) as persistence. The client provides a LiveScoring page used by scorers to record balls, extras and wickets. The server exposes REST endpoints for matches, players and teams, and manages persistence, auth and validation. The application is designed to be extended with more features (statistics, user roles, match imports).

Key goals of this guide: give a self-contained developer reference that makes it possible to add features and fix bugs without hand-holding. It includes component maps, data shapes, example flows, and common tasks.

High-level architecture

Runtime flow (simplified):

  1. User interacts with React client (browser). Live scoring UI keeps local UI state and posts changes to server via Axios API.
  2. Server (Express) receives REST requests, applies business logic and persists changes to MongoDB via Mongoose models.
  3. Server returns updated match object; client updates UI and local undo history.
  4. CI pipeline (GitHub Actions) runs tests and builds the client for deployment.

Technologies

  • Client: React 19 + TypeScript, MUI (Material UI), react-scripts (CRA), Axios, Jest/RTL
  • Server: Node.js + TypeScript, Express 5, Mongoose (MongoDB), Nodemailer
  • CI: GitHub Actions; builds and tests both client and server

Code structure & where to look

Top-level folders:

  • client/ — React app source code (TSX). Key directories:
    • src/pages — page-level containers (e.g., LiveScoring.tsx)
    • src/components — small UI components and dialogs
    • src/services — API wrappers (axios usage) in api.service.ts
    • src/utils — pure helpers (matchHelpers.ts) which should be unit-tested
  • server/ — Express server code
    • src/controllers — request handlers
    • src/models — Mongoose schemas (match.model.ts, player.model.ts, team.model.ts)
    • src/routes — route registration files
    • src/services — cross-cutting services (email, external integrations)
  • docs/ — documentation pages (this and app_overview.html)

Data model (match & innings)

The application centers on a Match document with an array of Innings. Typical fields (simplified):

Match {
  _id: string,
  team1: string|Team,
  team2: string|Team,
  overs: number,            // match length in overs
  currentInnings: number,   // 0 or 1
  innings: [ Inning, Inning ]
}

Inning {
  battingTeam: string|Team,
  bowlingTeam: string|Team,
  totalRuns: number,
  wickets: number,
  overs: number,    // e.g., 4.2 (overs.balls) or stored separately as balls
  balls: number,    // total legal deliveries
  battingStats: [{ player: string|Player, runs, balls, isOut, isOnStrike }],
  bowlingStats: [{ player: string|Player, overs, balls, runs, wickets }],
  currentOverBalls: [ BallOutcome ],
  recentBalls: [ BallOutcome ],
  extras: { wides, noBalls, byes, legByes, total }
}

BallOutcome { ballNumber, runs, isWicket?, extras?, timestamp, sequenceNumber }

Notes:

  • Some fields may be references (ObjectId) or embedded objects. API sanitizes before persisting.
  • Undo snapshots capture a subset of inning state (striker/nonStriker/bowler, strikerStats, bowlerStats, currentOverBalls, totals) to restore UI and game state.

API endpoints (key ones)

Server exposes REST endpoints under /api. Important routes:

PathMethodPurpose
/api/matchesGET, POSTList or create matches
/api/matches/:idGET, PUTGet or update match (score updates, innings updates)
/api/playersGETPlayers list
/api/teamsGETTeams list
/api/auth/*POSTLogin / token endpoints
/api/docs/docxPOSTAccepts HTML and returns .docx/.doc (docs helper)

Payload patterns

Score update flows typically send a fully cleaned match object; the server's controllers expect normalized IDs for teams/players. Use client/src/services/api.service.ts patterns to format payloads. See cleanMatchData helper inside LiveScoring for an example.

UI pages & major components

Important pages:

  • LiveScoring.tsx — the most complex page. Holds match state, undo history, bowler/striker selection flows and handlers for ball/outcome/extra/wicket. Extract presentational components where possible.
  • MatchList.tsx, MatchOverview.tsx — listing and match summary pages
  • Login.tsx — auth UI

Major components to reuse or extend:

  • OverControls — numeric buttons for scoring deliveries. It contains the Undo Icon button (recommended primary undo control).
  • PlayerSelectionDialog — pick players for striker/non-striker/bowler.
  • BallCommentary — renders recentBalls/currentOverBalls for commentary.

Local development & run instructions

Prerequisites

  • Node.js 18+ (compatible with dependencies)
  • npm 8/9
  • MongoDB (local or cloud) — set MONGODB_URI in server/.env

Run full stack locally

# from project root
# 1) Start server
cd server
npm install
# either build & run
npm run build
npm start
# or run in dev mode
npm run dev

# 2) Start client
cd ../client
npm install
npm start
# open http://localhost:3000 (proxy forwards API to server:5000)

Environment variables (server)

# sample .env (server/.env)
MONGODB_URI=mongodb://localhost:27017/street-cricket
PORT=5000
JWT_SECRET=your_jwt_secret
SMTP_HOST= (optional)
SMTP_USER= (optional)
SMTP_PASS= (optional)

Testing strategy

Unit tests

Put pure logic tests in client/src/utils/__tests__ and similarly for server util modules under server/test. Use Jest + ts-jest for TypeScript tests.

Integration / Controller tests

Use Supertest + Jest to spin up the Express app and assert API responses. Example server test flow:

import request from 'supertest';
import app from '../src/index';

describe('matches', ()=>{
  it('creates a match', async ()=>{
    const res = await request(app).post('/api/matches').send({...});
    expect(res.status).toBe(201);
  });
});

Manual end-to-end flows

  • Run server + client, create a match, start live scoring and exercise ball/outcome/extra/wicket flows.
  • Verify undo: create a few actions, then undo and ensure match/innings are restored to previous snapshot.

CI / GitHub Actions

Keep the CI simple and fast: install deps, run both client and server tests, and build the client. Use caching for node_modules. Example workflow is in docs/app_overview.html

Important checks for PRs:

  • Type-check (tsc) for both client and server
  • Run unit tests (Jest)
  • Optional: run linting (eslint) if configured

Common debugging scenarios

  • API 500 on update: inspect server logs (console), confirm request payload shape matches controller's expectation (check cleanMatchData logic in LiveScoring).
  • State mismatch after undo: check matchHelpers.applyUndoSnapshot and ensure it mutates or returns the expected fields; unit-test the helper.
  • Missing player IDs in DB: check whether Client sends object references vs IDs; ensure server expects IDs and uses Mongoose casting correctly.

Extending the application — practical guidance

1) Add a new UI feature

  1. Identify UI area (page/component). Create a small presentational component under client/src/components and add a container-level handler in the page under client/src/pages.
  2. Keep state localized and prefer props for presentation components. Move pure logic into client/src/utils for unit testing.
  3. Update the API contract only when necessary. Add server-side controllers/routes in server/src/controllers and server/src/routes.
  4. Add unit tests for both client helpers and server controllers. Run CI to validate changes before PR.

2) Add a new field to match model

  1. Add the field to Mongoose schema in server/src/models/match.model.ts. Provide a default value where appropriate.
  2. Update any server controllers that create/update matches to include/sanitize the new field.
  3. Update client code that reads/writes the match object (LiveScoring). Add conversion in cleanMatchData to persist only IDs where needed.
  4. Add tests to cover the new field behavior (serialization/deserialization, UI display).

3) Replacing/Upgrading a dependency (example: Mongoose)

  • Run npm install mongoose@x.y.z in server. Run npm run build and run tests.
  • Search code for breaking API changes (use editor search for deprecated functions).
  • Run integration tests and manual checks (create/update matches, live scoring flows).

Checklist before opening a PR

  • Run unit tests locally (client & server)
  • Run type-check (tsc)
  • Ensure linter (if any) is satisfied
  • Update docs (this guide or app_overview.html) for any API changes
